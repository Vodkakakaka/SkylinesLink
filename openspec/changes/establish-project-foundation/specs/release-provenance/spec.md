# Spec Delta

## Purpose

让使用者和贡献者能够核实 SkylinesLink 发行物的来源、许可与实际能力。通过明确源码和制品关系、第三方材料范围以及发布声明，维护原创贡献者的权益并避免分发不属于本项目的材料。

## ADDED Requirements

### Requirement: 原创源码按明确许可发布

项目 SHALL 使用 MPL-2.0 发布自身适用的原创源码，保留真实版权及来源声明；第三方材料依其实际许可单独标识，不声称本项目拥有第三方权利。

#### Scenario: 发行物包含第三方依赖
- **WHEN** 发行包包含第三方库或资源
- **THEN** 随包提供其适用许可及所需通知，并能从依赖记录确定来源和版本

### Requirement: 制品来源可追溯

每个正式发行物 SHALL 对应明确源码提交、构建环境、内容清单、校验值及验证结果；构建成功、客户端接入和游戏内验收必须分开报告。

#### Scenario: 仅离线构建通过
- **WHEN** 某版本完成构建但尚未完成游戏加载或客户端验证
- **THEN** 发布记录如实保留未验状态，不将其标为已完成真实使用验收

### Requirement: 工具链采用可复现的受支持版本

项目 SHALL 优先采用最新 LTS 运行时及稳定补丁，对无 LTS 分支的工具与依赖采用最新稳定版；记录官方游戏工具链兼容约束，固定实际构建版本与锁文件，不使用预发布版本或浮动 latest。JavaScript 依赖以 pnpm 管理，npm 仅备用；TypeScript 为项目开发依赖。

#### Scenario: 初始化或更新依赖
- **WHEN** 开发者选择或更新构建工具、语言及 SDK
- **THEN** 先核实官方稳定版本和游戏兼容边界，再锁定并验证实际构建；公开记录区分已选基线、本机已安装和实际制品所用版本

### Requirement: 随包运行时完整且符合分发条件

正式发行 SHALL 核对随包 Node 与 Host 的官方来源、校验值、许可证、组件匹配及平台接受情况，并在无开发工具的环境验证实际订阅内容；不得用开发机已安装工具掩盖运行依赖缺失。

#### Scenario: 上传工具可以收集运行文件
- **WHEN** 本机打包或上传器能收集 Node 可执行文件，但平台交付尚未验证
- **THEN** 发行记录仍保留平台和订阅待验状态，不据此宣称已支持完整订阅安装

### Requirement: 排除私人和专有内容

公共仓库及发行包 SHALL 排除私人存档、凭据、本机配置、无权再分发的游戏程序集和游戏反编译源码；需要游戏依赖的构建流程从使用者合法安装位置解析。

#### Scenario: 打包目录出现游戏程序集
- **WHEN** 发行检查发现包含不属于项目可分发内容的游戏文件
- **THEN** 打包检查失败并列明该文件，不继续发布该制品

### Requirement: 品牌和平台权利单独说明

发布资料 SHALL 清楚标明独立社区项目身份、官方发布地址和适用许可证，不暗示第三方官方背书；品牌说明不得削减标准开源许可证已经授予的代码权利。

#### Scenario: 第三方维护修改版本
- **WHEN** 第三方依法发布修改版本
- **THEN** 项目规则允许许可证授予的使用和分发，同时要求不得误导使用者将其认作本项目官方发布

### Requirement: 所有上传材料完成脱敏检查

项目 SHALL 在上传前检查实际公开材料中的敏感信息，覆盖源码、文档、待推送历史与提交元数据、日志、截图、调试符号和发行包；移除凭据及私人材料，必要示例采用占位符，不以部分暴露真实凭据作为脱敏方式。检查记录必须指向实际提交或制品，且不得泄露检出的敏感值。

#### Scenario: 提交元数据包含私人邮箱
- **WHEN** 待推送提交的作者或提交者邮箱为未经批准公开的私人邮箱
- **THEN** 上传检查失败，在该信息替换为适用的公开身份或隐私邮箱之前不推送该提交

#### Scenario: 文本扫描通过但附件尚未检查
- **WHEN** 源码扫描未发现敏感信息，但发行附件或截图尚未完成内容及元数据检查
- **THEN** 该附件仍标记为未验，不随已审材料上传

#### Scenario: 检查后发布内容发生变化
- **WHEN** 已审提交或发行包在上传前被修改
- **THEN** 对实际待上传版本重新检查，不沿用旧版本的检查结论

### Requirement: 两个渠道共用发行身份

发布流程 SHALL 为 GitHub 和 Paradox Mods 使用同一版本号、源码提交、更新日志及模组内容清单，提供一次启动的协调流程；两个渠道的实际版本和公开状态核实前不得报告全部发布完成。GitHub 提供源码及同版包，不成为普通订阅玩家的必需安装步骤。

#### Scenario: 一次正式版本发布
- **WHEN** 维护者启动指定源码提交对应版本的发布
- **THEN** 两渠道使用同一份已经验证的模组内容，并分别记录真实远端标识和可见状态

### Requirement: 部分发布可核对并继续

发布流程 SHALL 保留每个渠道的已知状态，在失败或回执未知后先核对实际远端事实，再继续缺失步骤；不得重复创建模组条目、盲目重发成功版本或用不同内容覆盖同一发行身份。

#### Scenario: 模组市场成功但 GitHub 发布失败
- **WHEN** Paradox Mods 已发布指定版本而 GitHub 步骤未完成
- **THEN** 流程标记部分完成，恢复时复用既有市场版本，仅完成缺失的 GitHub 步骤

#### Scenario: 上传返回超时
- **WHEN** 上传结果未知但服务端可能已经完成发布
- **THEN** 流程查询既有条目与版本，未排除成功前不重新创建或发布

### Requirement: 性能声明有可比较证据

发行验证 SHALL 记录同环境无模组基线、启用后空闲与代表性工作负载的资源及延迟测量，统计游戏和全部 Host 的资源总量与分项，覆盖单个及多个客户端，包含版本、场景和已建立预算的比较；未经测量不得将低占用、高性能或性能提升作为已验证结果。

#### Scenario: 只有单次正常调用成功
- **WHEN** 某版本仅验证一次工具调用但未完成资源和负载测量
- **THEN** 发布资料保留性能未验状态，不宣称已满足性能预算
